Writing code, slowly

I have been writing software since 1998, and for most of those years I have been writing it in a hurry. There was always a deadline, or a colleague waiting, or — more honestly — a feeling that the next thing was the thing that mattered, and so the current line had to be hurried past. Lately I have been trying the opposite. I treat a function the way I treat a paragraph: I leave it for a day, and read it the next morning before deciding it is finished.

The clearest sign of something written too quickly, for me, is that you cannot read it aloud. Good code, like good prose, has a cadence — the names rhyme, the lines breathe, and the reader's eye does not have to climb a fence to reach the meaning. Here is a small server I wrote on a Sunday morning. It does exactly one thing, and the one thing is small1.

1Smallness, for me, is not a constraint but a relief. A function I can hold in my head is a function I can fix at six o'clock on a Friday.

I keep a folder of legacy projects I still maintain for old friends and old companies — small PHP applications, mostly, of the kind that ran a corner of the internet in 2009 and continue, quietly, to run it now. There is a particular pleasure in returning to them. The functions are short. The names are dull. Nothing surprises you, which is the point2.

2The cliché says boring code is good code. I would put it more gently: code that does not call attention to itself is leaving room for the problem to.

The third thing I write every day is the journal — not in any application, but in a folder of plain text files. Three lines, sometimes four. The file for the day I cannot remember anything has the date and nothing else, and that, I have come to think, is also a record.

I have come to think that writing code slowly is just writing code with the radio off. There is no method. You sit at the desk. You read the line above. You decide whether the next one is needed. Most of the time, it isn't.
